# 로드맵과 경계

> 2026-11-10 — 오픈소스 라이브러리 운영 + 차트 사이트(TradingView·OpenMarket류) 운영으로 확장

## 1. 원칙: 라이브러리 vs 사이트

| | 라이브러리 (`@Funnest Charts/*`, Apache-2.0) | 사이트 (서비스) |
|---|---|---|
| 넣는 것 | 데이터 소스와 무관한 **표시·조작·인터페이스** | 특정 데이터·계정·서버가 필요한 **서비스 기능** |
| 예 | 차트 엔진, 툴바, 검색 UI, 지표, 그리기, Datafeed·TradingAdapter 인터페이스 | 로그인, 관심종목 동기화, 서버 저장 레이아웃, 알림, 스크리너, 뉴스, 커뮤니티, 유료 데이터 |
| 데이터 | "이런 모양으로 주면 그린다" (인터페이스) | 실제로 가져오는 코드 (어댑터 구현) |

사이트는 라이브러리를 그대로 사용한다(dogfooding). 사이트에만 필요한 기능은 라이브러리의 **슬롯·옵션·어댑터**로 끼워 넣고, 라이브러리 코드를 포크하지 않는다.

## 3. WebGL2 전환에 대한 판단

**결론: 지금 엔진을 WebGL2로 바꾸지 않는다. 대신 렌더러를 플러그인으로 교체 가능하게 만들고, WebGL2가 실제로 필요한 기능에만 쓴다.**

- 현재 Canvas2D 성능: 봉 3,600개와 이동평균선 4개를 한 프레임에 1.4ms로 그린다. 60fps 기준(16ms)에 여유가 크다. 일반적인 캔들 차트에서는 WebGL2로 얻는 이득이 없다.
- WebGL2가 이기는 곳: 데이터 점이 수십만 개 이상인 화면.
  - 호가 히트맵, 청산 히트맵
  - 풋프린트(가격대별 체결량) 차트
  - 틱 차트 장기 구간
  - 화면에 차트 9~16개를 동시에 띄우는 레이아웃
- WebGL2의 비용:
  - 글자(축 라벨 등)는 여전히 Canvas2D나 DOM으로 그려야 한다.
  - 브라우저는 동시에 쓸 수 있는 WebGL 컨텍스트 수를 제한한다(대략 16개). 다중 차트는 컨텍스트 하나를 공유하는 구조가 필요하다.
  - 모바일 GPU마다 동작 차이가 있고, 디버깅 비용이 크다.
- 진행 순서:
  1. core에 `SeriesRenderer` 인터페이스를 분리한다(캔들·라인·히스토그램 그리기를 교체 가능하게).
  2. 사이트에서 히트맵 같은 기능이 필요해질 때 `@Funnest Charts/webgl` 플러그인으로 추가한다.
  3. 글자, 오버레이, 그리기 도구는 Canvas2D를 유지한다(하이브리드).
